# Инфологическая модель медицинской лаборатории · IDEF1X

Модель реализована JPA-сущностями и миграцией V2. Применение к рабочей базе происходит при следующем запуске приложения. Описание реализации и проверки: [HIBERNATE.md](HIBERNATE.md).

Файлы: laboratory-idef1x.png — изображение; laboratory-idef1x.svg — векторный исходник; generate_model.py — исходник построения обеих версий (Python и Pillow).

## Нотация

PK расположен выше разделителя, остальные атрибуты — ниже. Все сущности имеют собственный ключ id_<имя таблицы>. FK называется <имя родительской таблицы>_id.
Все связи неидентифицирующие: FK не входит в PK потомка. Поэтому линии пунктирные, сущности прямоугольные. Черная точка обозначает сторону потомка; без уточняющего символа допускается 0..N потомков. Ромб у родителя обозначает необязательную ссылку (0..1 родитель). Без ромба ссылка обязательна (ровно 1 родитель). Отсутствие идентифицирующих связей не означает отсутствия обязательных ссылок.

Альтернативные ключи исключены из модели. Показаны только PK и FK. Символ ? — необязательное значение.

Все связи имеют тип «один ко многим» (1:N). Родитель может иметь 0..N дочерних записей. Необязательность ссылки у потомка не меняет тип связи на 1:1: она означает, что FK может отсутствовать. Например, поставщик отсутствует у документа выдачи, а ссылка на родительское подразделение отсутствует у корневого подразделения. Связей 1:1 и прямых связей M:N нет.

Источник обозначений: FIPS PUB 184, IDEF1X, разделы 3.5.2.3–3.5.2.4: https://www.idef.com/wp-content/uploads/2016/02/Idef1x.pdf

## Сущности и смысл связей

- units → materials: единица измерения применяется к материалам. Количество и цена указаны в этой единице.
- categories → materials: категория объединяет материалы.
- materials → material_batches: материал имеет партии с отдельными сроками годности и закупочной ценой.
- material_batches → inventory_document_items: каждая строка операции относится к одной партии.
- inventory_documents → inventory_document_items: документ содержит строки; черновик может быть пустым, проведенный документ должен иметь хотя бы одну строку.
- departments → departments: родительское подразделение объединяет группы; корневые подразделения не имеют родителя. Циклы запрещены.
- departments → users (1:N): подразделение объединяет пользователей; ссылка необязательна, поскольку сотрудник склада или администратор может не относиться к подразделению-получателю.
- warehouses → inventory_documents: документ изменяет остатки одного склада.
- users → inventory_documents: пользователь является автором документа.
- suppliers → inventory_documents: поставщик указывается при поступлении.
- departments → inventory_documents: подразделение является получателем выдачи.

## Структура лаборатории

В departments находятся только подразделения-получатели: Отдел клиентского сервиса; Производство (дочерние группы ВЭЖХ, ГХ, Элементный анализ, КДИ); Медофисы розничные. При необходимости отдельные медофисы становятся дочерними записями группы.

Склад хранится только в warehouses и не входит в departments. Поля departments_id в warehouses нет, прямой связи между этими сущностями нет. На старте один физический склад.

В выдаче warehouses_id обозначает склад-источник, departments_id — подразделение-получатель. Склад выдаёт, подразделение принимает. Возвратов из подразделений на склад, перемещений между подразделениями и выдач от подразделения не предусмотрено. Поступление от поставщика на склад и списание остаются отдельными операциями.

## Условия целостности

1. Типы документов: RECEIPT (поступление), ISSUE (выдача), WRITE_OFF (списание). Статусы первого этапа: DRAFT и POSTED.
2. Для RECEIPT поставщик обязателен, получатель-подразделение отсутствует. Для ISSUE получатель обязателен, поставщик отсутствует. Для WRITE_OFF обе ссылки отсутствуют, причина списания обязательна.
3. Проведенный документ содержит хотя бы одну строку, дату проведения и не допускает свободного редактирования. Черновики на остаток не влияют.
4. Количество положительное и может быть дробным. Цена единицы необязательна и неотрицательна. Полноценного денежного учета нет.
5. has_expiry у материала указывает, обязателен ли срок годности у его партий. Если да — expires_on обязателен. Если нет — допускается отсутствие срока. Это правило между таблицами потребуется обеспечить при реализации.
6. Каждая material_batches — отдельная учетная партия конкретного поступления. Повторное поступление с тем же номером производителя создает новую учетную партию. batch_number не уникален. Одна партия не должна повторно приходоваться в другом документе; это отдельное правило проведения.
7. Выдача сразу расходует материалы со склада. У получателей остатки не ведутся, дальнейшие отправки клиентского сервиса не регистрируются.
8. Остатки вычисляются по партиям и складам: проведенные поступления минус проведенные выдачи и списания. Отдельной таблицы остатков нет.
9. При проведении расхода необходимо предотвращать отрицательный остаток, в том числе при одновременной работе пользователей. Просроченные партии выдавать нельзя. Границу включительности expires_on следует зафиксировать в требованиях.
10. Срок годности и закупочная цена партии после проведения поступления не должны свободно изменяться.
11. role хранится атрибутом users с ограниченным набором значений; самостоятельная сущность ролей пока не требуется. Пароли хранятся только как хеши.
12. Альтернативные ключи в этой модели не задаются. Все сущности идентифицируются собственными PK. Ограничения для прикладных операций будут уточняться при реализации.

Служебная flyway_schema_history на предметную модель не включается. Выбор конкретных SQL-типов, индексов, способов реализации ограничений и миграций относится к следующему этапу.
